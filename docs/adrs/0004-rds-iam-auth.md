# ADR-0004: Database authentication — IAM auth vs password in Secrets Manager

**Status:** Accepted
**Date:** 2026-08-27
**Deciders:** nephast

## Context

Compass stores document chunks and embeddings in RDS PostgreSQL. Something has to
authenticate to it, and the question is what credential that something carries.

The original acceptance criterion for COMPASS-13 said "connect from a pod using an
IRSA-scoped IAM role". EKS was deferred to the end of the build, so the criterion
was re-cut to a VPC-attached Lambda — which is the caller that matters for the
ingestion pipeline anyway. That re-cut is itself informative: the database applies
the same mechanism regardless of who calls it, and the *identity of the caller* is
an IAM trust-policy concern, not a database one. Pod, Lambda and EC2 instance
differ only in how they obtain credentials.

**Threat model.** What is being defended against: a durable database credential
leaking out of the application path — an environment variable, a log line, a
stack trace, a developer laptop, a CI secret — and being replayed by someone who
has network access. What is explicitly *not* being defended against here: an
attacker who already holds broad IAM permissions in the account. That is
COMPASS-8's problem (permission boundaries), and COMPASS-8 is currently cut.

**Established facts:**

- The database is `db.t3.micro`, PostgreSQL 17.11, in private subnets, `publicly_accessible = false`, reachable only from the `compass-dev-app` security group.
- `rds.force_ssl = 1`; the parameter is static and applies at boot.
- pgvector 0.8.2 is installed.
- An IAM auth token is a locally computed SigV4 signature over hostname, port and username. Generating one makes no network call. It is valid for 15 minutes.
- The token is validated **at connect time only**. An established connection is never re-checked and survives token expiry indefinitely.
- RDS caches IAM authentication decisions, denials included, for several minutes.
- The master password is generated by RDS (`manage_master_user_password`), has never been known to a human, lives in an RDS-owned Secrets Manager secret, and **rotates automatically every 7 days** with no rotation Lambda of ours.
- `rds-db:connect` produces **no CloudTrail event**. Token generation is local, and the connection is client-to-database.

## Decision

The application authenticates to PostgreSQL with a short-lived IAM auth token; no
database password exists anywhere in the application path.

The master password still exists, and must. `GRANT rds_iam` can only be issued by
a password-authenticated superuser, so IAM auth cannot bootstrap itself. Nor can
that door be closed afterwards: granting `rds_iam` to the master user would
destroy the only bootstrap and recovery path, and RDS exposes no `pg_hba.conf` to
disable password authentication wholesale. **Password authentication therefore
remains permanently available for exactly one role, `compass_admin`.** Enabling
IAM auth on the instance adds a mechanism; it removes nothing.

## Options Considered

### Option A: IAM database authentication

| Dimension | Assessment |
|-----------|------------|
| Complexity | High — bootstrap SQL, a manual runbook, TLS becomes mandatory |
| Cost | Free |
| Scalability | Token generation is free and local, but new connections carry an IAM-checked rate ceiling that password auth does not |
| Team familiarity | Low |

**Pros:** No durable credential in the application path. The app's credential is
regenerated per connection and useless after 15 minutes. Revocation is an IAM
policy detach rather than a password change plus redeploy. Works identically for
Lambda, pods and EC2 — only the trust policy changes.

**Cons:** Bootstrap cannot be automated in Terraform. Connection-rate ceiling on
new connections. Coarse attribution — every caller is the same database role.
Higher conceptual load for anyone joining.

### Option B: Password in Secrets Manager with scheduled rotation

| Dimension | Assessment |
|-----------|------------|
| Complexity | Low |
| Cost | Per secret per month, plus API calls |
| Scalability | High — no per-connection auth ceiling |
| Team familiarity | High |

**Pros:** What most teams do. Works with any client, driver and tool, including
ones with no AWS SDK. No bootstrap step. No connection-rate ceiling. Rotation is
tunable — it is not fixed at 30 days, and for an RDS-managed secret AWS performs
it without a rotation Lambda.

**Cons:** The application must hold, cache and refresh a durable credential, and
notice when it changes without dropping connections. Every place that credential
is stored is a place it can leak, and each leak is good until the next rotation.

## Trade-off Analysis

**The attack IAM auth actually stops.** An application-path leak. Under Option B
the password reaches every caller — Lambda environment, pod, `.env`, CI, a
laptop, occasionally a log line. Each is a leak site, and a leaked password is
good for the whole rotation interval from anywhere with network access. Under
Option A the application never holds a durable credential at all; what leaks is a
token that expires in 15 minutes.

The gain is therefore not "no password exists" — it is **reducing the number of
places a durable credential exists, from many to one.**

**The attack it does not stop.** An attacker who obtains
`secretsmanager:GetSecretValue` on the master secret authenticates by password as
`compass_admin`, which is `rds_superuser`. That path does not touch IAM: no
token, no `rds-db:connect`, no policy evaluation. IAM authentication does
precisely nothing about it. What defends it is **network position** — the
database is private and admits only `compass-dev-app`, so a stolen secret is
useless from outside the VPC — plus scoping of `GetSecretValue` itself, which is
COMPASS-8's job and is currently cut. Both of those protect Option B equally.

**Is the 15-minute window real or cosmetic?** Partly cosmetic, and worth saying
so. The token is validated at connect time only, so an attacker who opens a
connection inside the window keeps it indefinitely; expiry does not evict anyone,
and neither does detaching the policy. The window bounds **acquisition of new
connections**, not access. What makes it real rather than theatre is the leak
surface, not the clock: a 15-minute token that never leaves the process is a much
smaller target than a 7-day password distributed to every caller.

**Rotation is not the differentiator.** Both options end up with exactly one
durable credential, machine-generated and auto-rotating — the master secret
rotates every 7 days either way. The difference is who has to cope with it:
under Option A, nobody; under Option B, the application.

## Consequences

**Easier:**

- Revocation is an IAM policy detach, not a password change and redeploy. (Live sessions survive it — see below.)
- The same permission policy serves Lambda, pods and EC2; only the trust policy differs. The IRSA path at COMPASS-6 is a trust-policy change and nothing else.
- No application code ever handles a database password.

**Harder:**

- **TLS is now mandatory, not optional.** `sslmode=require` is unsafe here: it skips certificate verification, and verification is what stops a token being intercepted and replayed for its full lifetime. `verify-full` with the RDS CA bundle, always.
- Bootstrap cannot live in Terraform. `docs/runbooks/database-bootstrap.md` exists because of this decision, and is a manual step on every fresh instance.
- New connections carry an IAM-checked rate ceiling that varies by instance class. This interacts with Lambda concurrency at COMPASS-11; the mitigation on this budget is reserved concurrency, not RDS Proxy.
- Attribution is coarse. Every caller authenticates as `compass_app`, and `rds-db:connect` generates no CloudTrail event, so IAM gives authorisation but no audit trail. Per-connection attribution needs `pgaudit` and log exports — deferred to COMPASS-29.

**To revisit:**

- Revocation does not terminate established sessions. If that gap ever matters, it needs `pg_terminate_backend` or an instance reboot, and should be written down as an incident step.
- The proof role for COMPASS-13 held five permissions because a human at a prompt needs to *find* things. The ingestion Lambda needs one, `rds-db:connect`. Do not use the runbook's throwaway role as the template for a workload role.
- Trigger for revisiting the whole decision: a client that cannot generate SigV4 tokens, or a connection-rate ceiling reached in practice.
